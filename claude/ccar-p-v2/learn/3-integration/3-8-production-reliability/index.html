    Production Reliability Controls

    Exam skillProduction Reliability Controls

    Analyzing the failure pattern in error traces or throughput data from a production integration, and specifying the reliability control (rate-limit handling, retry and backoff, idempotency for side-effecting tools, or fallback routing) that addresses it without introducing duplicate effects.

    Read the failure pattern in error traces and throughput data, and apply the reliability control that fixes it (rate-limit handling, retry with backoff, idempotency for side-effecting tools, or fallback routing) without creating duplicate effects.

    Written and maintained by Prakash Sridharan, Claude Certified Architect

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    Production integrations fail in patterns, and each pattern has its own control. The exam gives you error traces or throughput data and asks for the control that fixes the pattern without introducing duplicate effects. The second half of that sentence is where most wrong answers fail.

    Classify the failure first

    Pattern in the tracesWhat it meansControl
    Bursts of 429 errors at peak or when a batch job startsRequests exceed a rate limitBackoff with jitter that honours retry-after; separate limits for workloads that compete
    Brief 500 or 529 errors on a small share of requestsTransient server or overload errorsRetry a small number of times with backoff
    Overloaded errors that last many minutesA sustained capacity problemFallback routing to a tested alternate model or provider
    400 errors on the same requests every timeThe request itself is invalidDo not retry; fix or reject the request
    Duplicate payments, bookings or emails after timeoutsA side effect completed before the client saw the result, and a retry repeated itIdempotency keys on side-effecting calls
    A tool failure that ends the conversation, or a retry storm after an outageErrors are not handled at the tool boundaryReturn the error as a tool result; add a circuit breaker

    Retries and backoff

    Retry only what can succeed on a later attempt. Exponential backoff with jitter spreads retries out so many clients do not retry at the same instant, and the retry-after header says when to try again. Immediate retries in a loop multiply the load at the worst moment. Separate workspaces with their own limits stop a batch job from starving an interactive service that shares the same organization.

    Idempotency for side-effecting tools

    A retry is only safe if repeating the call cannot repeat the effect. When a tool creates an order, issues a refund or sends a message, the request carries an idempotency key, and the receiving system returns the original result when it sees the same key again.

    The key must identify the business action, not the attempt:

    Key built fromResult
    The order, refund or booking it represents (for example a requisition ID and approval ID)Every retry, by the client or by Claude in a later turn, carries the same key, so duplicates are refused
    A random value per HTTP attemptEach retry looks new; duplicates get through
    The tool_use ID of the callA retry Claude makes in a later turn is a new call with a new ID; duplicates get through
    A timestampSeparate actions can collide, and retries that cross the boundary slip through
    Decision rule
    Retries meet side effects only through a key

    Before any retry policy touches a tool that changes the world, the tool must accept an idempotency key derived from the business action. Fewer retries make duplicates rarer; only the key makes them impossible.

    Fallback routing

    When the primary model is unavailable for longer than retries can cover, route requests to an alternate model or provider that has already passed the evaluation's quality floor, and record every fallback so the team can see how often it happens. A fallback that has never been evaluated trades an outage for a quality incident.

    Errors at the tool boundary

    A failed tool call should return to Claude as a tool result marked as an error, saying what failed and whether retrying later may help, so the agent can tell the user or try another path. An exception that ends the conversation, or an empty result that looks like "nothing found", are both failures of the integration. During a partner outage, a circuit breaker stops calling the failing service after repeated errors and tries again later, which prevents a retry storm when it recovers.

    Example
    Refunds issued twice

    During a sale, a retailer's refund tool timed out on some calls after the returns system had already issued the refund. The client wrapper retried, and customers were refunded twice. Longer timeouts and fewer retries reduced the duplicates but did not stop them. Adding an idempotency key built from the return ID made every retry return the original refund.

    Exam trap
    A prompt instruction as the guard

    "Check whether the payment already exists before calling the tool again" relies on the model, and the retry often happens in client code the model never sees. Duplicate effects need an enforced guard.

    Exam trap
    Batch processing as a rate-limit fix for live actions

    Moving synchronous, side-effecting actions into a batch job changes throughput, not the semantics of duplicates, and it breaks the response time the user expects.

    In the exam

    Reliability items show error traces or throughput figures from a production integration and ask which control addresses the pattern without creating duplicates. Classify first: rate limits call for backoff and separate limits; brief server errors for bounded retries; long overloads for tested fallback routing; invalid requests for no retry; duplicate side effects for idempotency keys built from the business action. Distractors reduce how often a race happens instead of removing it, rely on prompt instructions, or retry without bound.

    Check your understanding

    Question 1

    A payments agent's client retries every timed-out call. Traces show duplicates only where the payment had already executed before the timeout. Which change resolves it?

    Show answer

    Answer: C. The effect completed before the client saw it, so any retry repeats it. A key derived from the payment request lets the payments system return the original result. Timeouts reduce the race; prompts and batches do not address it.

    Question 2

    Which errors should a client not retry?

    Show answer

    Answer: B. A malformed request fails the same way every time, so retrying wastes calls and load. The other errors are transient and clear with backoff.

    Question 3

    The primary model returns overloaded errors for 25 minutes during a peak. A second model has passed the quality floor on the evaluation set. What is the right control?

    Show answer

    Answer: D. A long overload outlasts sensible retries, so a tested fallback keeps the service up. An endless loop or an error page fails customers, and a permanent switch gives up the better model for no reason.

    Apply it: Make Hollis & Grant's refund agent reliable at peak

    Exercise · about 20 minCase: Hollis & Grant Home

    Hollis & Grant's support agent looks up orders in the Order Management System and creates returns and refunds through the Returns portal API. During last year's peak, at 2.5 times normal volume, the traces showed: 429 errors in bursts at the start of each hour, when the help-centre re-indexing job ran; about 40 duplicate refunds after Returns portal timeouts; and 15 minutes of overloaded errors from the primary model, during which chat showed an error.

    1. Classify each failure and name its control.
    2. Design the idempotency key for refunds, and say why the obvious alternatives fail.
      Done when: a retry by the client or by the agent in a later turn cannot create a second refund.
    3. Specify the fallback and the condition that triggers it.
    4. Choose two signals to monitor that would show the controls working during the next peak.
    Check your work
    Show model answer

    1. Classification

    FailureControl
    429 bursts each hourBackoff with jitter honouring retry-after; move the re-indexing job to its own workspace with a lower limit, outside chat's capacity
    Duplicate refunds after timeoutsIdempotency key on every refund call
    15 minutes of overloadFallback routing to a second model already evaluated against the chat quality floor

    2. Key. Built from the return ID and the refund line it pays, created when the return is approved and reused by every later call for that refund. A random key per attempt or the tool call's ID changes on each retry and would let duplicates through; a timestamp could merge two refunds or miss a retry.

    3. Fallback. After two retries with backoff on overloaded errors for a chat request, send it to the second model and log the fallback; return to the primary when its error rate drops. Refund actions still go through the Returns portal with their keys, whichever model drafted the reply.

    4. Signals. Duplicate-key hits on the Returns portal (retries safely absorbed), and the fallback rate with chat's 95th-percentile first response time during the peak.
