    Deployment Surfaces and Agent Runtimes

    Exam skillDeployment Surface and Agent Runtime Selection

    Selecting a deployment surface (Anthropic API, Amazon Bedrock, Google Vertex AI, Microsoft Foundry) and an agent runtime (Messages API loop, self-hosted Agent SDK or headless Claude Code, Claude Managed Agents) under data residency, compliance, model-availability, and operational-ownership constraints, and justifying the trade-offs the selection imposes on latency, feature availability, hosting, session state, sandboxing, and data custody.

    Choose where Claude runs (the Claude API, Amazon Bedrock, Google Vertex AI or Microsoft Foundry) and what runs the agent loop (your own Messages API loop, the Agent SDK or headless Claude Code, or Claude Managed Agents), and name the trade-off each choice imposes.

    Written and maintained by Prakash Sridharan, Claude Certified Architect

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    Two decisions sit underneath every Claude architecture, and the exam treats them as one skill: where the model is served (the deployment surface) and what runs the agent loop (the agent runtime). Constraints such as data residency, compliance agreements, model availability and who will operate the system usually decide both before any prompt is written.

    Deployment surfaces

    SurfaceWhat it gives youWhat you give up
    Claude API (Anthropic)New models and features first; the full feature set, including Message Batches, Files, Agent Skills, the MCP connector and Managed AgentsData is processed by Anthropic, outside your cloud account
    Amazon BedrockInference inside the AWS security boundary, AWS identity and billing, regional endpoints for residencySome features are not offered (for example Message Batches, Agent Skills, the MCP connector and Managed Agents); new features can arrive later
    Google Vertex AIInference inside Google Cloud, with its identity, billing and regionsFeature availability differs from the Claude API
    Microsoft FoundryClaude inside Azure, Azure billing and identitySome features, including Managed Agents, are not supported

    Feature lists change, so the exam does not test the exact list; it tests the reasoning. When a residency or boundary obligation applies, the cloud provider's surface usually wins, and the team accepts feature lag and the work of filling the gaps itself.

    Decision rule
    Where versus how long

    Data residency is about where data is processed. Zero data retention is about how long it is kept. A retention setting never satisfies a residency obligation.

    Agent runtimes

    RuntimeWho runs the loop, state and sandboxFits
    Your own Messages API loopYou: every turn, tool call and piece of stateFine-grained control, custom workflows, any surface
    Agent SDK, self-hostedYou host it; the SDK provides the loop, tools, permissions and hooksAgents that must run beside your own systems, under your control
    Headless Claude CodeYou run it in CI or scriptsCoding tasks as pipeline steps
    Claude Managed AgentsAnthropic hosts the harness, sessions and cloud sandbox; you send eventsLong-running or scheduled work with minimal infrastructure

    Managed Agents keeps session history, sandbox state and outputs on Anthropic's side so sessions can pause and resume. That is what makes it convenient, and it is also why it is not eligible for zero data retention or HIPAA BAA coverage (self-hosted Managed Agents is the exception for zero data retention), and why it is only available on some surfaces.

    Name the binding constraint and the trade-off

    The exam's typical item lists three or four wishes that cannot all be met, then asks which one decides the design and what the organization accepts.

    1. Find the hard constraint. A legal obligation (residency attested in the firm's cloud, a BAA requirement) outranks a preference (newest features, no infrastructure to run).
    2. Pick the surface and runtime that satisfy it.
    3. State what is given up: feature lag, owning the agent loop and session state, building your own sandbox, or higher latency.
    Example
    Contract analysis in a regulated firm

    A firm's legal team requires that documents and model inputs stay inside its cloud provider, where it holds its residency attestations. The product team wants new features as soon as they ship, and the platform team would like Anthropic to host the agent loop. Residency binds: the firm deploys through its cloud provider's surface and accepts that features arrive later and that it runs the agent loop and its session state itself.

    Exam trap
    "All three requirements are satisfied"

    Options that claim no trade-off is needed are usually wrong. Surface choice constrains both the runtime options and the features available.

    Exam trap
    Copying data out to reach a feature

    Mirroring documents to the Claude API so a feature is available still sends model inputs outside the boundary the obligation protects.

    In the exam

    Items describe an organization's obligations and preferences (residency, a compliance agreement, model or feature needs, how much the team wants to operate) and ask which surface and runtime fit and what trade-off follows. Find the obligation that is legally binding, choose the surface and runtime that satisfy it, and name what is given up: feature availability, hosting, session state, sandboxing or data custody. Reject answers that use zero data retention to meet a residency rule or claim that nothing is traded away.

    Check your understanding

    Question 1

    A bank's attestations require all model inference to stay inside its AWS account boundary. The team also wants Message Batches for a nightly job. What follows?

    Show answer

    Answer: B. The boundary obligation decides the surface. Bedrock does not offer Message Batches, so the team builds the job from real-time requests. Retention settings do not move inference into AWS, and batch data is covered by the same obligation.

    Question 2

    Why is Claude Managed Agents not eligible for zero data retention?

    Show answer

    Answer: C. Managed Agents is stateful by design: sessions keep history, files and outputs server-side so they can resume. That convenience is what rules out zero data retention, except for self-hosted Managed Agents.

    Question 3

    A team with two platform engineers wants an agent that runs for hours each night with a sandbox, and has no residency obligation. Which runtime fits best?

    Show answer

    Answer: D. Little operations capacity and no residency obligation favour the managed runtime, which hosts the loop, sessions and sandbox. The other options all make the small team build or babysit infrastructure.

    Apply it: Choose Prairie State's surface and runtime

    Exercise · about 20 minCase: Prairie State Mutual

    Prairie State wants Claude to extract claim fields and draft acknowledgements for 18,000 claims a month. EU claimants' data must be processed in the EU and US customers' data in the US, injury claims contain health information, and the IT team would prefer not to run agent infrastructure.

    1. List the constraints and mark which are obligations and which are preferences.
    2. Choose the deployment surface or surfaces, and say how EU and US claims are routed.
      Why: residency is an obligation, so it decides before any preference.
    3. Choose the agent runtime, and say why the preferred managed runtime does or does not fit.
    4. Name the trade-offs Prairie State accepts, in one sentence each.
    Check your work
    Show model answer

    1. Constraints. Obligations: EU data processed in the EU, US data in the US; health information handled under the insurer's compliance agreements; licensed adjusters make every denial. Preferences: no agent infrastructure to run; new features early.

    2. Surface. A cloud provider's surface with regional endpoints, one in an EU region for EU claims and one in a US region for US claims. The intake service routes each claim by the claimant's jurisdiction before any model call. A global endpoint is not used, because it can route a request to another region.

    3. Runtime. The extraction and drafting steps are short, bounded calls, so a Messages API workflow run by Prairie State's own intake service fits; it needs no long-lived sessions. Claude Managed Agents would remove infrastructure work, but it stores sessions on Anthropic's side, is not offered on every surface and is not covered for health information, so it does not fit the obligations.

    4. Trade-offs. Prairie State runs its own workflow service and its state. Some features reach its surface later than the Claude API. Regional endpoints may cost more than global routing.
