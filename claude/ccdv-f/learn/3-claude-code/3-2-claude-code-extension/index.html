    Extending Claude Code for a Team

    Exam skillClaude Code Customization and Extension

    Analyzing a repeatable team workflow to choose the extension mechanism that fits it, whether a Skill, plugin, Rules file, hook, subagent, or slash command, and authoring and packaging that extension for distribution.

    Match a repeatable team workflow to the right Claude Code extension (Skill, plugin, rules file, hook, subagent or slash command), write it so it loads or runs when it should, and package it so it installs and works on every teammate's machine.

    Written and maintained by Prakash Sridharan, Claude Certified Architect

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    Pick by what the workflow needs

    NeedExtensionWhy
    Must happen every time, or never (format after edits, block a path)HookRuns as code at a lifecycle event
    A procedure used sometimes (release checklist, API-client generator)SkillOnly name and description load until a task matches
    Run only when typed (/deploy-check)Skill with disable-model-invocation: trueInvoked by name, never by the model
    Guidance for one part of the codebaseRules file in .claude/rules/ with pathsLoads only for matching files
    Bulky work whose details the main session does not need (review a large diff)SubagentSeparate context, returns a summary; own tool list
    Share a whole setup across the team or many reposPluginBundles Skills, hooks, subagents and MCP servers, versioned
    Rules for one repo, shared with whoever clones itProject .claude/ folderCommitted with the code
    Decision rule
    Enforce in hooks, teach in Skills

    A Skill cannot block a tool call, and a hook cannot teach a procedure. "Block edits to infra/prod/" is a hook or deny rule; "how to change infrastructure safely" is a Skill.

    Writing a Skill that gets used

    A Skill is a folder with SKILL.md (YAML front matter plus instructions) and optional scripts or reference files. Claude decides whether to load it from the name and description, so the description must say what it does and when to use it, using the words people actually type. A longer body does not help selection; it is read only after the Skill is chosen.

    Subagents

    Define them in .claude/agents/ with a description, a prompt and a tool list. They start with a clean context: they do not inherit the parent's loaded Skills, so list the Skills a subagent needs in its definition. Restrict tools to enforce a role (a reviewer gets read-only tools).

    Packaging a plugin

    • Bundle every script and file the plugin needs; reference them with ${CLAUDE_PLUGIN_ROOT} (or $CLAUDE_PROJECT_DIR for project files). Never use the author's absolute paths or globally installed tools.
    • Document required environment variables and declare dependencies.
    • Plugin commands are namespaced: /payments:run-tests. Renaming the plugin renames its commands.
    • Distribute through a marketplace. Organizations can restrict allowed marketplace sources and pre-register approved ones in managed settings.
    Exam trap
    Deny rules do not travel by accident

    A guardrail the author had in their own settings is not in the plugin unless it is bundled. If a Skill depends on a hook for safety, ship the hook.

    In the exam

    Items describe a team workflow or a broken extension and ask which mechanism fits or what to fix. Match "always/never" to hooks, "sometimes" to Skills, "one area" to rules files, "bulky and separate" to subagents, and "share and version" to plugins. Distractors put procedures in CLAUDE.md, enforcement in Skills, or machine-specific paths in plugins.

    Check your understanding

    Question 1

    A 12-step release checklist is needed only when preparing a release. Where should it live?

    Show answer

    Answer: C. A Skill loads only when the task matches its description.

    Question 2

    A custom subagent ignores the team's api-review Skill that the main session uses. Why?

    Show answer

    Answer: A. A subagent starts clean and gets only what it is given.

    Question 3

    A plugin's hook calls /Users/sam/tools/check.sh and fails for teammates. Fix?

    Show answer

    Answer: D. Bundled files referenced through the plugin root resolve on every machine.

    Apply it: Package Quarry Lane's team setup

    Exercise · about 20 minCase: Quarry Lane Software

    Quarry Lane wants: Prettier on every edited file; no edits to infra/prod/; a release-notes procedure used about once a week; a review of large diffs that should not flood the main session; and SQL migration rules for db/migrations/ only. All 60 engineers should get the same version.

    1. Map each need to an extension.
    2. Write the release Skill's front matter.
    3. Describe the plugin and how it is distributed and controlled.
      Done when: nothing depends on a single engineer's machine.
    Check your work
    Show model answer

    1. Prettier: PostToolUse hook on edit tools. infra/prod/: PreToolUse hook (and a managed deny rule). Release notes: Skill. Large diffs: a read-only review subagent that lists the review Skill it needs. Migrations: .claude/rules/migrations.md with paths: ["db/migrations/**"].

    2.

    ---
name: release-notes
description: Drafts release notes from merged PRs since the last tag, in Quarry Lane's format. Use when asked for release notes, a changelog or "what shipped".
---

    3. Plugin "ql-dev" bundles the hooks (scripts inside the plugin, called through ${CLAUDE_PLUGIN_ROOT}), the Skills, the subagent and the docs MCP server, with a version number and README listing required environment variables. It is published in Quarry Lane's internal marketplace; managed settings allow only that marketplace and pre-register it.
