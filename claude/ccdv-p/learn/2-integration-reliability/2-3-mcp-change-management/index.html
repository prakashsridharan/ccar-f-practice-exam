    Production MCP and Change Management

    Exam skillProduction MCP and Change Management

    Applying production MCP operation and change-management practice to MCP server deployments, model version migrations, and prompt updates, including remote MCP deployment and authentication, tool and schema versioning, migration testing against breaking behavior changes, platform-specific configuration parity and gateway/routing architectures, prompt versioning, and progressive rollout with rollback.

    Run MCP servers, model versions and prompts as production changes, with authenticated remote servers, backward-compatible tool schemas and deprecation, pinned snapshots tested against behavior changes, configuration parity across platforms and gateways, versioned prompts, and staged rollouts with rollback.

    Written and maintained by Prakash Sridharan, Claude Certified Architect

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    In a Claude system, behavior changes come from more places than code: an MCP server's tool definitions, the model snapshot, the system prompt, a gateway between clients and the API, and the configuration for each platform. Each needs the discipline of a production release: versioning, testing, staged rollout, a rollback path and a record of what was live when.

    Remote MCP servers

    A remote MCP server is a shared service that many agents call. Its security posture follows the MCP authorization and security guidance:

    • Authenticate clients with OAuth and validate that each token was issued for this server (its audience).
    • Never pass the client's token through to downstream APIs. The server obtains its own credentials, scoped to what its tools need. Token passthrough breaks audience checks and creates confused-deputy risks.
    • Authorize per user when the server acts for users, rather than one powerful service credential for every request.

    When an agent uses a third-party server, expose only what it needs. With the Messages API MCP connector, disable the server's tools by default and enable the required ones, and give the server a token scoped to the same access.

    Tool and schema versioning

    ChangeEffect on callersPractice
    Add an optional parameter with a defaultNoneShip it
    Add a required parameterBreaks every callerMake it optional, or publish a new tool version
    Change the output formatBreaks callers that parse itNew version beside the old one
    Remove a toolBreaks its callersDeprecate with a dated plan

    Deprecation needs usage data (who still calls the old version), warnings the callers will see (a notice in the tool's result), a dated removal plan, and escalation when owners do not respond. Changing a format in place, or forcing everyone to update on the same day, causes incidents.

    Dependencies that change independently, such as a vendor's MCP server, need their versions recorded with each trace and pinned where possible, so a behavior change can be matched to a dependency change in minutes.

    Model versions and migration

    Pin production to a dated snapshot ID. An alias points at the newest snapshot and can change behavior without a deploy. Treat each model change as a release:

    1. Read the migration guide's behavior changes, such as more literal instruction following or parameters that are no longer supported.
    2. Refresh the evaluation suite with recent production cases, including failures; a suite every model passes cannot show a difference.
    3. Compare results by category and field by field, including output format, not only the pass rate.
    4. Review prompts for implicit expectations the new model may follow more literally.
    5. Canary on a small share of traffic, watching quality, length and cost, then widen.
    6. Finish before the retirement date.
    Example
    The canary that caught a cost regression

    A new snapshot on 5% of traffic left task success unchanged but made outputs 45% longer and conversations 30% more expensive. The team paused, adjusted prompts for length, and re-ran the canary before widening.

    Prompts as versioned configuration

    Keep prompts in version control with IDs, and log the prompt version on every trace. Then any response can be traced to the prompt that produced it, and rollback is a configuration change.

    Progressive rollout for prompts:

    • release to a small share first, widening in stages while quality and error metrics hold;
    • define rollback triggers in advance and keep the previous version ready;
    • keep online monitoring on even when offline evaluation passed.

    Platform parity and gateways

    When the same agent runs on the first-party API and on Bedrock, Vertex AI or Foundry, configuration drifts unless it is generated from one versioned source with per-platform settings (model identifiers, supported features) and a parity check. Run the evaluation suite on each platform before promotion.

    An LLM gateway is the right place for cross-cutting controls: central credential management, per-application quotas, consistent logging. It must forward what the API needs, including version and beta headers; a gateway upgrade that strips them breaks features that still work when called directly. It is the wrong place for silently rewriting prompts, overriding the model an application asked for, or requiring approval of every prompt change.

    Exam trap
    Coupled changes

    Shipping a model change together with a new tool that depends on it makes rollback partial: reverting the model breaks the tool's route. Ship changes so they can be rolled back separately, or roll them back as a unit.

    In the exam

    Change-management items describe a change that broke something, or a change about to ship. Look for the missing discipline: backward compatibility, a version record, a pinned snapshot, a refreshed evaluation, a staged rollout, a parity check, or a gateway that alters requests. Distractors announce changes in chat, restart everything, rely on aliases, freeze prompts forever, or cut over on the deadline.

    Check your understanding

    Question 1

    A team adds a required parameter to an existing MCP tool and two downstream teams' automations break. What practice prevents this?

    Show answer

    Answer: C. A new required parameter breaks every existing caller. Additive changes and explicit versions let callers migrate at their own pace.

    Question 2

    Production uses a model alias, the alias moved, and a parser failed for six hours. What should the team do?

    Show answer

    Answer: B. A pinned snapshot changes only when the team releases the change, after evaluation.

    Question 3

    A remote HR MCP server forwards each user's corporate token to the HR API. What should it do instead?

    Show answer

    Answer: A. Token passthrough breaks audience checks. The server authenticates its clients and calls downstream with credentials of its own.

    Apply it: A release process for Tidewater's assistant

    Exercise · about 30 minCase: Tidewater Analytics

    Tidewater had two change incidents this quarter: a prompt change shipped to all tenants at once made answers ignore dashboard filters for large tenants, and the CRM connector vendor changed a tool's output format overnight, breaking report creation for 140 tenants for six hours. Tide also has a model migration due before its snapshot retires next quarter.

    1. Write the release steps for a prompt change, from merge to 100% of tenants.
    2. Design controls for the third-party CRM server so a vendor change is caught fast or prevented.
    3. Plan the model migration, including what the evaluation compares.
    4. List what every trace must record to support all three.
    Check your work
    Show model answer

    1. Prompt release. Prompt files live in Git with version IDs. A change must pass the evaluation suite (with per-segment results for large and small tenants). Rollout: internal tenants, then 5% of tenants for 48 hours, then 25%, then all, watching groundedness on sampled traffic, filter-respect checks and escalations by segment. Rollback triggers (for example, a 3-point groundedness drop in any segment) are agreed before release; the previous version stays deployable with one flag.

    2. CRM server. Pin the server version where the vendor allows it. Record the server version and a hash of its tool definitions on each trace, and alert when the hash changes. Run a nightly contract test of the report flow against the live server. Enable only the CRM tools Tide uses, with a tenant-scoped, read-only token where possible.

    3. Migration. Pin the new dated snapshot in a branch. Refresh the evaluation set with the last month's failures and complex multi-filter questions. Compare groundedness, filter respect and answer format by tenant segment, plus cost and length per answer. Canary at 5% with the same rollback triggers, then widen, finishing a month before retirement.

    4. Trace fields. Prompt version, model snapshot ID, MCP server versions and tool-definition hash, gateway route, tenant segment, and the evaluation run that approved the release.
