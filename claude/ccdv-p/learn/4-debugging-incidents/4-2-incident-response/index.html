    Incident Response and Learning Loops

    Exam skillIncident Response and Learning Loops

    Evaluating incident-response options during an LLM-system outage or quality regression, including triage, mitigation, rollback, and communication, and converting the incident into regression evaluations, monitoring coverage, and postmortem findings.

    Lead an LLM-system incident from triage to mitigation, rollback and communication, including quality regressions with no errors, and turn every incident into regression evaluations, monitoring coverage and blameless postmortem actions.

    Written and maintained by Prakash Sridharan, Claude Certified Architect

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    LLM systems have the usual incidents (outages, dependency failures, capacity problems) and some of their own: quality regressions with no errors, after a prompt, model, index or tool change. The response pattern is the same: triage, mitigate first, communicate, then learn. What differs is that the most likely causes are changes to non-code components, and the most valuable learning output is a new evaluation case.

    Triage

    • Is it real, and how bad? Impact (users, money, safety), scope (which routes, tenants, categories) and trend.
    • What changed? Deployments, prompt and model versions, index rebuilds, MCP server versions, provider status. The trace version attributes and change log answer this quickly.
    • Who leads? An incident commander coordinates; responders investigate; one person communicates.

    Mitigate first

    Mitigation does not need the root cause.

    SituationMitigation
    A recent release correlates with the regression and a tested rollback existsRoll back now, then diagnose and fix forward
    One category behaves wrongly, cause unknownA feature flag that stops that behavior (for example, route that claim category to adjusters)
    A dependency is degraded for daysCircuit breaker, honest degraded messaging, keep the rest working
    A bad retrieval indexRoll back to a known-good index with a small freshness gap
    Provider capacity incidentBounded retries, tested fallback, queued non-urgent work

    Waiting for the engineer's fix while customers see wrong interest rates, adding a warning banner, or shutting down working features are worse trade-offs.

    Exam trap
    Coupled rollbacks

    If a model change and a dependent tool shipped together, rolling back one breaks the other. Release changes so they can be rolled back separately, or as a unit.

    Communicate

    Post the impact, what users can do, and when the next update will come, then keep to that cadence. Waiting for the root cause, or describing a provider incident as "maintenance", erodes trust. Record a timestamped timeline as you go, from change events, alerts and actions, rather than reconstructing it from memory a week later.

    AI first responders

    An agent in the on-call channel can read alerts, dashboards and recent deploys and post a diagnosis within minutes. Consequential actions, such as a rollback, wait for the on-call engineer's approval, and everything it finds and does is recorded in the incident thread. In tiered automation, the highest tier may run only pre-approved runbooks and must hand its findings to humans; it never merges code changes directly.

    Remediate what already happened

    A fix stops new damage; it does not correct the 3,000 customers who already received a misleading message or the claims already approved. Identify affected records from logs and correct them. When a provider announces a quality issue that affected your window, use your own traces to find the affected requests.

    Learning loops

    OutputExample
    Regression evaluationThe incident's cases (multi-currency quotes, medication dosages) added to the release gate
    Monitoring coverageThe signal that would have caught it sooner (refusal rate per route) with an alert and an owner; check similar signals for the same gap
    Runbook updateTriggers for quality incidents, and rollback steps for prompts, models and indexes
    Contributing factorsSystem conditions: an evaluation coverage gap, a release to all traffic at once

    Postmortems are blameless: people describe what happened candidly when they are not blamed, which exposes the conditions that allowed the failure. Action items are specific, owned and enforced by the system. "Be more careful" is not an action item.

    In the exam

    Incident items put you mid-incident or in the postmortem. Choose the action that contains harm fastest without waiting for root cause, communicates clearly, or converts the incident into durable protection. Distractors wait, freeze all releases, blame individuals, roll back everything, delete evidence, or treat a deployed fix as the end of the work.

    Check your understanding

    Question 1

    A prompt release correlates with wrong interest rates, and a one-command rollback exists. The engineer expects a fix in an hour. What first?

    Show answer

    Answer: A. Mitigate first when a tested rollback exists. The fallback model runs the same faulty prompt.

    Question 2

    A postmortem finds a change passed an evaluation suite that had no medication-dosage cases, and shipped to all traffic at once. Which contributing factors belong in it?

    Show answer

    Answer: C. Contributing factors are system conditions that lead to concrete fixes, not personal blame.

    Question 3

    An agent misled 3,000 customers before a fix was deployed. What follow-up matters most?

    Show answer

    Answer: B. Remediation for those already affected is part of the response, alongside the learning actions.

    Apply it: Run Granite's fraud-agent incident

    Exercise · about 25 minCase: Granite Federal Bank

    At 09:40, analysts report that the fraud-review agent is closing cases as "not fraud" for card-testing patterns it used to flag. A prompt change and a new MCP version of the device-data server both shipped at 08:15. 140 cases have been closed since then. The fraud operations manager wants to know what happens next.

    1. Write the first three actions in order, with who does each.
    2. Draft the first status update to fraud operations.
    3. Plan remediation for the 140 cases.
    4. List the postmortem outputs, with owners.
    Check your work
    Show model answer

    1. First actions.

    • The incident commander declares the incident and assigns roles (09:45).
    • The on-call engineer disables automatic closing for card-testing patterns with a feature flag, so those cases stay open for analysts (mitigation without root cause).
    • Responders check traces split by prompt version and device-server version for the closures since 08:15, and roll back whichever change carries them; if unclear, roll back both, since they were released separately and can be reverted independently.

    2. Status update. "Since 08:15 the fraud agent has closed some card-testing cases incorrectly. Automatic closing for that pattern is now off, and those cases will stay open for analysts. We are reviewing the 140 cases closed since 08:15. Next update at 10:30."

    3. Remediation. Query the audit log for cases closed since 08:15 with card-testing signals; reopen them and assign them to analysts by priority; notify affected customers through the normal fraud process where cards were used after closure.

    4. Postmortem outputs. Regression cases for card-testing patterns in the release gate (fraud ML lead); a close-rate-by-pattern monitor with control bands (platform team); separate canary releases for prompt and MCP version changes (release manager); a timeline built from audit events (incident commander). Blameless, with contributing factors stated as system conditions.
