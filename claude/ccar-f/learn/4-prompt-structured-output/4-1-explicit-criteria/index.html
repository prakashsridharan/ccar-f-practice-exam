    Explicit Criteria and False Positives

    Exam taskDesign prompts with explicit criteria to improve precision and reduce false positives

    Precision comes from saying exactly what to report and what to skip, with severity defined by concrete examples, not from asking Claude to be conservative. Noisy categories can be switched off while they are fixed.

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    Vague instructions do not move precision

    "Be conservative", "only report high-confidence findings" and "be very, very careful" sound like they should cut false positives. In practice they change little, because they do not tell Claude what counts. Precision improves when the prompt defines the categories to report and the ones to skip.

    VagueExplicit
    "Check that comments are accurate""Flag a comment only when the behaviour it claims contradicts what the code does"
    "Only report important issues""Report: bugs that change behaviour, security issues, data loss. Skip: style, naming, patterns used consistently elsewhere in this repository"
    "Be conservative""If the issue depends on an assumption you cannot verify from the diff, do not report it"

    False positives destroy trust in everything

    Developers do not judge categories separately. If the style category is wrong 70% of the time, they start dismissing all findings, including accurate security ones. A high false-positive category damages the categories that work.

    A practical response: temporarily disable the noisy category so developers trust the rest again, and improve its prompt offline before re-enabling it.

    Define severity with examples

    "Critical" and "minor" drift unless each level is defined with criteria and a concrete code example:

    SeverityCriteriaExample
    CriticalExploitable security flaw or data loss in productionSQL built by string concatenation from request input
    HighWrong behaviour users will hitRefund calculated before discount is applied
    MediumWrong behaviour in rare pathsMissing null check on an optional field
    LowMaintainabilityDuplicated helper that already exists in utils
    Decision rule
    Categories, not confidence

    Tell Claude which issues to report and which to skip, and define each severity with an example.

    Exam trap
    Adding intensity

    "Be very, very conservative" and "only report if you are certain" are the distractors. They have no measurable effect in the scenarios the exam describes.

    Exam trap
    Leaving the noisy category on while tuning

    Every day it stays on, trust in the accurate categories keeps falling.

    In the exam

    Scenario 5 again: a reviewer with a high false-positive rate, developers ignoring all findings, or inconsistent severity labels. The answer defines report and skip categories, uses examples for severity, or disables a noisy category temporarily.

    Check your understanding

    Question 1

    A review prompt says "only report high-confidence findings" and false positives stay at 35%. What should change?

    Show answer

    Answer: C. Explicit categories tell Claude what counts. Confidence wording and intensity do not change what it considers an issue.

    Question 2

    The style category has a 70% false-positive rate and developers now ignore security findings too. What is the best immediate step?

    Show answer

    Answer: B. Turning off the noisy category restores trust in the accurate ones. Improve its prompt offline and re-enable it once it is reliable.

    Question 3

    Nearly identical issues are labelled critical one day and minor the next. What fixes this?

    Show answer

    Answer: A. Criteria plus concrete examples anchor each level, so similar issues get the same label.

    Apply it: Rewrite Keystone's review criteria

    Exercise · about 15 minCase: Keystone Payments

    Keystone's reviewer says "be thorough but conservative". Write explicit criteria.

    1. List what to report and what to skip, at least four of each.
    2. Define four severity levels with one Keystone-specific code example each.
    3. Decide what to do with the style category now, and what must be true before it returns.
    Check your work
    Show model answer

    1. Report and skip

    ReportSkip
    Logic errors that change payment amounts or statesFormatting the linter already enforces
    Security issues: injection, secrets, card data exposureNaming preferences
    Missing error handling on calls to the card networkPatterns used consistently elsewhere in the repo
    Concurrency bugs on shared balancesComments, unless they contradict the code
    Data loss on retriesSpeculative issues needing facts outside the diff

    2. Severity

    LevelExample
    CriticalFull card number written to logs
    HighRetry path charges the customer twice
    MediumMissing timeout on the fraud-check call
    LowDuplicate currency-format helper

    3. Style. Disable it now. Re-enable it only after the new criteria reach a false-positive rate the team agrees (for example under 10%) on a sample of 100 past pull requests.
