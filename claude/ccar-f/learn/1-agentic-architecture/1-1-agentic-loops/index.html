    The Agentic Loop and stop_reason

    Exam taskDesign and implement agentic loops for autonomous task execution

    An agent is Claude in a loop. Your code sends the conversation, reads stop_reason, runs the tools Claude asked for, appends the results and repeats until Claude ends its turn.

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    The Messages API is stateless. Claude never runs a tool itself and never remembers the last call. An agentic loop is the code you write around the API that makes repeated calls look like one autonomous piece of work.

    Each pass through the loop does four things:

    1. Send the full conversation so far, with the tool definitions, to Claude.
    2. Inspect stop_reason on the response.
    3. If it is "tool_use", execute every tool Claude requested, in your code.
    4. Append Claude's response and a tool_result for each tool call to the history, then go back to step 1.

    When stop_reason is "end_turn", Claude has finished and the loop stops.

    messages = [{"role": "user", "content": request}]
while True:
    response = client.messages.create(model=MODEL, max_tokens=4096,
                                      tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": response.content})
    if response.stop_reason != "tool_use":
        break                      # end_turn, or a case handled below
    results = []
    for block in response.content:
        if block.type == "tool_use":
            output = run_tool(block.name, block.input)
            results.append({"type": "tool_result",
                            "tool_use_id": block.id, "content": output})
    messages.append({"role": "user", "content": results})

    Two details carry marks in the exam. Each tool_result must carry the tool_use_id of the call it answers, and the results go back in a user message. That is the only way the model sees what a tool returned.

    Other stop reasons

    "tool_use" and "end_turn" are the two that drive the loop, but a robust harness handles the others explicitly rather than treating them as success.

    stop_reasonMeaningTypical handling
    end_turnClaude finished its turnStop; use the final response
    tool_useClaude wants one or more tools runRun them, append results, continue
    max_tokensOutput hit the token limit mid-responseTreat as incomplete: continue or raise the limit, never present it as done
    stop_sequenceA configured stop sequence was emittedTreat like an end of turn unless that sequence has a special meaning for you

    The Agent SDK runs this loop for you. You still need to understand it, because the SDK's turn limits, budgets and hooks all attach to these same steps.

    Model-driven, not scripted

    In an agentic loop Claude decides which tool to call next, based on what earlier results showed. That is different from a pre-configured decision tree or a fixed sequence of tool calls written in your code. The model-driven loop handles cases nobody scripted; a fixed sequence is cheaper and more predictable when the steps never change (lesson 1.6 covers that choice).

    Decision rule
    Let stop_reason end the loop

    The loop continues while stop_reason is "tool_use" and stops when it is "end_turn". Everything else is a safeguard, not the stopping rule.

    Exam trap
    Anti-patterns the exam offers as answers
    • Parsing Claude's text for phrases like "I'm done" or "issue resolved" to decide when to stop.
    • Stopping when the response contains any text. Claude often writes text and requests a tool in the same response.
    • An iteration cap (for example, stop after 10 calls) as the primary stopping mechanism. A cap is a sensible safety net against runaway loops, but it cuts off legitimate long tasks and lets nothing finish on its own terms.
    • Assuming the API or an MCP server feeds tool results to the model automatically.
    Example
    A refund lookup, step by step

    A customer asks about a late order. Claude's first response requests get_customer (stop_reason tool_use). The harness runs it and appends the result. Claude then requests lookup_order; the harness runs that too. On the third call Claude writes a reply to the customer and stops with end_turn. Nothing in the harness decided the order of those calls: Claude chose each one from what the previous result showed.

    In the exam

    Expect a harness with one flaw. Common ones: the loop stops on text content; it stops after a fixed number of iterations; tool results are not appended, so Claude repeats the same call; a max_tokens response is shown to the customer as a finished answer. Pick the option that makes stop_reason the control signal and keeps the history complete.

    Check your understanding

    Question 1

    Your harness stops the loop whenever Claude's response contains a text block. Some sessions end before the refund is issued. Why?

    Show answer

    Answer: B. A single response can hold a text block ("Let me check that order") and a tool_use block. Stopping on text throws away the tool call. Only stop_reason tells you whether Claude is done.

    Question 2

    After running lookup_order, how does the model see the order data?

    Show answer

    Answer: D. The API is stateless. The result reaches the model only when your code appends a tool_result block, tied to the call by tool_use_id, and sends the conversation again.

    Question 3

    A response arrives with stop_reason "max_tokens". What should the harness do?

    Show answer

    Answer: A. max_tokens means the output was cut off mid-response. Showing it as a finished answer is a classic way for sessions to end in an undefined state.

    Apply it: Write Cedar Ridge's loop contract

    Exercise · about 15 minCase: Cedar Ridge Outfitters

    Cedar Ridge's platform engineer wants a one-page "loop contract" before writing the support agent's harness. Write it.

    1. Define the continue and stop rules. State exactly which stop_reason values continue the loop, which end it, and what happens on each of the others.
    2. Describe how a tool result returns to Claude. Name the block type, the field that links it to the call, and the role of the message it goes in.
    3. Add one safety net and say why it is not the stopping rule. For example a turn limit or a budget.
      Why: the exam treats caps as safeguards, never as the main stop.
    4. List three anti-patterns the code review must reject.
    Check your work
    Show model answer

    1. Continue and stop rules

    stop_reasonAction
    tool_useRun every requested tool, append results, call Claude again
    end_turnStop; the last response is the reply to the customer
    max_tokensIncomplete: call again asking Claude to continue; if it repeats, escalate with context
    stop_sequenceTreat as end of turn (we configure none today)
    anything else, or an API errorDo not reply as if resolved; escalate with the case so far

    2. Returning results. For each tool_use block, run the tool and add a tool_result block whose tool_use_id equals the block's id. All results for one response go together in a single user message appended after Claude's assistant message.

    3. Safety net. A limit of 25 turns per session. Real sessions use 4 to 10, so hitting 25 means something is looping; the harness then escalates with a summary instead of answering. It is a guard against runaway cost, not the way a normal session ends.

    4. Reject in review

    • Stopping when the response contains text.
    • Searching Claude's text for "resolved" or "anything else?" to decide the session is over.
    • Stopping after a fixed number of tool calls as the normal end of a session.
