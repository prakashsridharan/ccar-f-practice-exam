Context Windows and Token Usage

Exam taskOptimize context windows and manage token usage

Decide what goes into the context window and when, using monolithic, progressive, retrieval and compaction strategies, and prevent the two different ways a request can run out of room.

On this pageWhat you need to knowIn the examCheck your understandingApply itSources

What you need to know

Prompt engineering is about the instructions. Context engineering is about everything else the model sees: which documents, tool results and history are in the window, when they arrive, and how long they stay. It drives quality, cost and latency at the same time.

What fills the window

Every call carries the system prompt, tool definitions, the conversation so far, retrieved documents, tool results and the space needed for the answer (plus thinking, if enabled). Anything outside the window does not exist for that call.

A bigger window is not automatically better. More tokens cost more and take longer, and long, cluttered context makes the relevant detail harder to find. The goal is the smallest set of high-signal tokens that lets the model do the step in front of it.

Four things that are easy to confuse

ConceptWhat it isWho owns it
Context windowWhat the model can see on this callThe request you build
RetrievalFetching relevant knowledge at the time of the questionYour retrieval layer
Application stateThe authoritative record: orders, cases, patientsYour systems of record
Memory and summariesSelected facts carried between calls or sessionsYour application (or a memory tool you provide)

The API does not remember previous calls. If a conversation, a decision or an identifier needs to persist, your application stores it and sends it again.

Four strategies

StrategyIdeaFitsMain risk
MonolithicLoad everything needed up frontBounded tasks with predictable inputs that need all the material at onceCost and clutter as content grows
ProgressiveLoad only what the next step needsMulti-step workflows, agents, long conversationsDropping something an earlier step needed
RetrievalFetch relevant pieces at question timeLarge or changing knowledge, citationsRetrieval misses the right passage
CompactionSummarize accumulated history and continueLong-running agents and sessions near the limitLosing exact identifiers, numbers and decisions

Real systems combine them. A coding agent might start with a full task description, add files progressively as it explores, retrieve documentation on demand, clear old tool results it no longer needs, and compact its history after many turns.

Decision rule
Compaction must keep the facts that matter

A summary that loses an account number, a dosage or a decision is worse than no summary. Tell the compaction step exactly what to preserve verbatim, or keep those facts in structured application state instead.

Two different ways to run out of room

  1. The request is too large to send. The prompt is over the model's token limit (rejected as an invalid request) or the request body is over the byte limit (rejected as too large). Nothing is generated.
  2. The request fits, but the answer runs into the ceiling. Generation stops early with a stop reason saying the context window was exceeded, and the output is cut off.

Prevention is mostly measurement: count tokens before sending large requests, read the usage figures on every response, reserve room for the output, and trim what does not earn its place (old tool results, repeated instructions, whole documents where a section would do).

Example
An agent that kept everything

A research agent re-read 40 web pages per task and carried every page in its history. By the end, each call held over 150,000 tokens, costs had tripled and answers had become vaguer. Clearing tool results once they had been summarized into notes, and keeping those notes in structured state, cut the context by 80% and improved the answers.

Exam trap
"Use a bigger context window"

When a scenario shows rising cost, slower responses or degraded answers in long sessions, the larger-window option is usually the distractor. First stop sending what is not needed.

Exam trap
Expecting the API to remember

Options that assume Claude recalls an earlier call, or that the conversation persists on its own, are wrong. The application carries state forward.

In the exam

Context questions describe long documents, long sessions or growing agents, often with a symptom: the request is rejected, answers are cut off, answers get worse late in a session, or costs climb. Identify which of the two failure modes it is, pick the strategy that fits the data and the task, and look for compaction that preserves identifiers. Be suspicious of options that only enlarge the window or rely on the model's memory.

Check your understanding

Question 1

A long report generation stops mid-sentence, and the response reports that the context window was exceeded. What happened?

Show answer

Answer: D. The request was accepted, so the input fit. Generation then hit the window ceiling, which is reported as its own stop reason with truncated output.

Question 2

A support agent forgets the customer's order number after compacting a long conversation. What is the best fix?

Show answer

Answer: C. Exact identifiers must survive. Holding them in structured state, and instructing the compaction step to keep them verbatim, solves the loss without giving up compaction.

Question 3 · select 2

Which TWO statements about context are true?

Show answer

Answer: A, D. Your application carries state between calls, and stale tool results can be cleared to keep the window focused. More context is not automatically better, and retrieval fetches knowledge while application state is the authoritative record.

Apply it: Plan context for discharge summaries

Exercise · about 20 minCase: Lakeview Regional Medical Center

Lakeview's discharge-summary drafter must handle typical stays of 30,000 tokens and long stays of up to 140,000. Design how the drafter fills its context window.

  1. Classify the inputs: which go in whole, which are fetched as needed, and which come from systems of record rather than notes.
  2. Design the approach for long stays, so quality does not drop on the patients with the most complex care.
    Why: long stays are where summaries matter most and where cluttered context hurts most.
  3. Decide what must be carried verbatim between steps, and where it is stored.
  4. Add the checks that prevent the two out-of-room failures.
Check your work
Show model answer

1. Inputs

InputHandling
Admission note, discharge-day progress noteLoaded whole: always needed
Daily progress notesProgressive: summarized by day, then the day summaries are used
Consult and procedure reportsLoaded whole when referenced in the hospital course
Discharge medicationsFrom the pharmacy system, inserted by code; never extracted from notes
Pending results, follow-up appointmentsQueried from the EHR and scheduling system at draft time

2. Long stays. A two-stage map-reduce: first, one call per day of notes produces a structured day summary (events, decisions, changes in treatment, with note references). Second, the drafter writes the hospital course from the day summaries plus the admission and discharge notes. Every call stays well under the window, and each statement keeps a reference back to its source note for the physician's review.

3. Verbatim facts. Patient identifiers, allergies, procedure names and dates, and the references to source notes are kept in structured state and passed to each call as data; the summaries are told to copy them exactly. Medications never pass through a summary at all.

4. Checks. Count tokens before each call and split further if a day's notes are unusually long; reserve space for the 1,500-token summary; monitor usage and the context-exceeded stop reason; and route any stay that still fails to a physician-written summary rather than a truncated draft.
