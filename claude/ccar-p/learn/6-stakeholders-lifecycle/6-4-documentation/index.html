    Documenting Architectures for Handoff

    Exam taskDocument architectures and provide implementation guidance

    Document architectures so a successor can change them safely and an auditor can verify them, with decision logs that record the rejected options and the reasons, an assumption register, runbooks and a control register.

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    The architect who designed a system will not run it forever. A successor who inherits diagrams and code but not the reasons will, sooner or later, "simplify" something that was there for a reason: switch to a global endpoint, remove an approval step, drop a log field. Documentation exists to prevent that, and to let auditors check that controls are real.

    The completeness test

    Decision rule
    Could a competent stranger change it safely?

    If an architect who was not involved could read the documentation and make a change without breaking a requirement, it is complete. If they would have to guess why something is the way it is, it is not.

    Decision logs with rationale

    A decision record captures more than the choice:

    FieldExample
    DecisionUse the cloud platform route with the region set explicitly
    Alternatives rejectedThe global endpoint; the direct API
    Trade-off resolvedSimpler configuration versus the data-residency obligation
    RationaleCustomer contracts require in-region processing; the global endpoint could route elsewhere
    OwnerPlatform lead
    EvidenceRegional configuration export; data-flow record
    AssumptionsThe contract requirement covers logs as well (confirmed by legal, March)
    Revisit whenA new region is needed, or the provider changes regional options

    The rationale and the rejected alternatives are the most valuable fields for a successor, and the ones most often missing.

    Two audiences, different artifacts

    For the person taking overFor the compliance reviewer
    Explains intentArchitecture diagram, decision log, assumption registerControl register (obligation, control, owner)
    Shows evidenceDeployment runbook, test and evaluation resultsControl register with links to evidence
    ArtifactRecords
    Assumption registerWhat is not yet confirmed, and who will confirm it
    Decision logWhat was chosen, what was rejected, and why
    Architecture diagramComponents, data flows, trust boundaries
    RunbookHow to deploy, operate, roll back and respond to incidents
    Evaluation summaryWhat was tested, on what data, with what results
    Control registerObligations mapped to controls, owners and evidence

    Implementation guidance for builders

    Handoffs also go forward, to the team that builds. Give them the requirements with sources, the decisions with rationale, the success criteria and evaluation set, interface contracts (tool definitions, schemas), the prompt templates and their versioning rules, and the non-negotiables ("medication lists are inserted by code, never generated"). For AI systems, prompts, model versions and evaluation sets are part of the design and need the same care as code.

    Keep it alive

    Documentation drifts like configuration. Update the decision log when decisions change, re-date assumptions when confirmed, and plan for known future events, such as a model version being retired, with a note on how to migrate and what to re-evaluate.

    Example
    The approval step that looked redundant

    A new team lead removed the supervisor approval on refunds over $250, reasoning that the assistant "already checks the policy". There was no record that the approval existed because finance auditors required it. The decision log entry, had it existed, would have said: "Rejected: model-only policy check. Reason: finance audit requires named approver for refunds over $250."

    Exam trap
    Diagrams as documentation

    A diagram shows what exists, not why. Options that consider a diagram plus code "complete documentation" miss the decision rationale.

    Exam trap
    Test results as compliance evidence

    A test summary shows that something was tested once. Compliance reviewers need a control register with current evidence that each control operates.

    In the exam

    Documentation questions ask what a handoff package is missing, which artifact serves which audience, or what would have prevented a successor's mistake. The answer is usually the decision log with rationale and rejected alternatives, the assumption register, or the control register with evidence, matched to the audience.

    Check your understanding

    Question 1

    A successor switches a regulated workload to a global endpoint to simplify configuration, breaking a residency requirement. Which artifact would most likely have prevented this?

    Show answer

    Answer: D. The successor needed to know that the global endpoint was considered and rejected for a residency reason. Only a decision log with rationale says that.

    Question 2

    An auditor asks how the organization knows its human-approval control is working. What should be provided?

    Show answer

    Answer: C. Auditors need evidence that the control operates, with an owner. Diagrams and designs show intent; pre-launch tests show only a moment in the past.

    Question 3 · select 2

    Which TWO fields make a decision record most useful to a successor?

    Show answer

    Answer: A, D. Rejected alternatives and rationale tell a successor what not to "simplify" and why.

    Apply it: Document Northgate's in-product assistant

    Exercise · about 20 minCase: Northgate Software

    The architect who designed Northgate's in-product assistant for banks (lessons 3.1 and 3.8) is moving to another team. Prepare the handoff.

    1. Write three decision records with all the fields in this lesson: the delivery route, per-bank workspaces, and minimal content logging.
      Done when: each has rejected alternatives and a rationale.
    2. List four assumptions for the assumption register, with owners.
    3. List the handoff package for the successor and, separately, what the SOC 2 auditor will receive.
    Check your work
    Show model answer

    2. Assumptions

    AssumptionOwner
    No bank requires processing outside its own countryAccount management
    Banks accept usage-based chargebackFinance
    30-day sampled content meets support needsSupport lead
    The current model version stays available for at least 12 monthsPlatform lead (track deprecation notices)

    3. Handoff package. For the successor: architecture diagram with trust boundaries, the decision log, the assumption register, prompt templates with version history, the evaluation set and latest results, tool and schema definitions, the runbook (deploy, roll back, tenant onboarding, incident response) and the governance table. For the auditor: the control register (tenant isolation, access control, logging limits, retention, vendor approval) with links to current evidence.
