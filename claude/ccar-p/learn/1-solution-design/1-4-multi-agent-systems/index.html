    Multi-Agent Systems and Orchestration

    Exam taskDesign multi-agent systems and orchestration strategies

    Know when an orchestrator with subagents is worth its cost, and design the decomposition, result format, conflict handling and failure recovery deliberately.

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    A multi-agent system splits work between two roles.

    • The orchestrator owns the goal. It breaks the work into sub-tasks, decides what to delegate, and combines the results into one answer. It coordinates rather than doing the sub-task work itself.
    • Subagents own scoped sub-tasks. Each runs in its own context window, completes one piece, and returns a result to the orchestrator.

    When it is worth it

    Multiple agents help when the work is broad and separable: many sources to research, many documents to review, many independent directions to explore. Each subagent gets a clean context focused on its piece, so the work is not squeezed into one crowded window, and independent pieces can run in parallel.

    They cost more. Every subagent carries its own instructions and context, so token use rises sharply compared with a single agent, and coordination adds latency and new failure points. Anthropic's write-up of its research system reports that multi-agent runs used many times the tokens of a chat interaction. That trade is worth making for high-value, parallel work and wasteful for tightly coupled tasks where every step depends on the last.

    Decision rule
    Multi-agent for breadth, not for sequence

    If the sub-tasks are independent, parallel subagents can pay off. If each step needs the previous step's full result, a single agent or a chained workflow is cheaper and easier to debug.

    Three things you must design, not assume

    1. Decomposition. How the goal is split, and how much each subagent is told. Vague task descriptions lead to duplicated work or gaps; each subagent needs a clear objective, boundaries and an expected output.
    2. Result structure. Subagents should return results in a consistent, structured format, so the orchestrator can combine them without guessing.
    3. Conflict resolution. When two subagents disagree or leave a gap, the orchestrator needs an explicit rule (prefer the more authoritative source, flag the conflict, or escalate to a person) rather than silently picking one.

    Failures are not equal

    Where a failure happens decides whether it can be recovered.

    FailureWhere it landsDesign response
    A subagent returns nothing or malformed outputThe subagent boundary: recoverableValidate every result; retry or reassign the unit; record the gap instead of failing the whole run
    Subagents return conflicting resultsThe synthesis step: recoverableApply a stated conflict rule or escalate
    The orchestrator loses its goal or its partial synthesisThe orchestrator: often unrecoverableCheckpoint its state so a run can resume rather than restart
    Traces scatter across agentsObservability: affects everythingPass one trace ID through every agent so a run can be reconstructed

    Two practical consequences follow. Make subagent work idempotent, so a retry cannot double-apply an effect. And reconcile coverage at synthesis: the number of results should equal the number of units sent out, so a silently dropped subagent is noticed.

    Example
    Supplier contract due diligence

    An acquirer must review 100 supplier contracts before closing. The orchestrator splits them into one task per contract and sends them to subagents in parallel. Each subagent returns the same structured fields: change-of-control clauses, termination rights, liability caps, a risk rating. The orchestrator checks it has 100 results, retries any that failed validation, flags contracts where the risk rating conflicts with the clauses found, and writes the summary report from checkpointed partial results.

    Exam trap
    Multi-agent as the default "advanced" answer

    Options that add an orchestrator and specialist agents to a simple, sequential task are distractors. More agents mean more cost, latency and failure points.

    Exam trap
    Treating every failure the same

    A scenario that loses the orchestrator's state is a different problem from a single failed subagent. Retrying subagents does not help when the coordinator's progress is gone; checkpointing does.

    In the exam

    Questions in this area usually present a working multi-agent design with one weakness: missing trace IDs, no conflict rule, no validation of subagent output, no checkpoint, or no check that every unit came back. Pick the option that fixes the stated weakness at the right boundary. If the scenario asks whether to use multiple agents at all, weigh independence of the sub-tasks against the extra token cost.

    Check your understanding

    Question 1

    When does a multi-agent design most clearly justify its extra token cost?

    Show answer

    Answer: C. Subagents pay off when work is broad and separable, because each gets a focused context and they can run in parallel. Tightly sequential or latency-critical work is cheaper and simpler with one agent or a workflow.

    Question 2

    A research run's orchestrator crashes after 40 of 60 subagents have returned. Which design would have limited the damage most?

    Show answer

    Answer: B. Subagent failures are recoverable at their boundary; losing the orchestrator's state is not. Checkpointing lets the run resume with the 40 results it already has instead of starting again.

    Question 3

    A due-diligence report covers 97 of 100 contracts and nobody notices. Which control would have caught it?

    Show answer

    Answer: A. A coverage check at synthesis (results received equals units dispatched) makes a silently dropped subagent visible. Spot checks and better models can still miss three missing results.

    Apply it: Plan the migration audit

    Exercise · about 20 minCase: Northgate Software

    Northgate's platform team must audit all 160 services for the deprecated logging library within two weeks. By hand that is about 400 engineer-hours. Design a multi-agent audit that a platform engineer could run and trust.

    1. Decide whether multi-agent fits. Use the independence of the work units to justify it, and name what the orchestrator does and does not do.
    2. Define the subagent's task and its result format. List the fields every subagent must return.
      Why: the orchestrator can only combine results that share one structure.
      Done when: a "not sure" answer is possible and carries evidence.
    3. Build the failure matrix. For at least four failures, say where each lands and the design response.
    4. Make coverage provable. Say how the final report shows that all 160 services were audited, and what happens to the ones that were not.
    Check your work
    Show model answer

    1. Fit. Each service can be audited without knowing anything about the others, so the work is broad and separable: a good fit for parallel subagents with clean, focused contexts. The orchestrator reads the service catalogue, sends one task per service, validates and combines results, and writes the report. It does not audit code itself.

    2. Task and result format. Task: "Audit service X in repository Y for use of the old logging library. Read only; change nothing." Each subagent returns:

    FieldValues
    service, repository, owning teamFrom the catalogue
    uses_old_libraryyes / no / unclear
    call_sitesNumber found
    patternse.g. direct calls, wrapper class, configuration only
    risklow / medium / high, with a one-line reason
    evidenceFile paths and line numbers
    confidencehigh / medium / low

    3. Failure matrix

    FailureWhere it landsResponse
    Subagent returns empty or malformed outputSubagent boundaryValidate against the format; retry once; then mark "needs human audit"
    Repository too large for one contextSubagentSplit by module; one subagent per module, merged per service
    Two runs disagree on a serviceSynthesisRule: "yes" with evidence beats "no"; otherwise flag for the owning team
    Orchestrator crashes mid-runOrchestratorResults written to storage as they arrive; the run resumes from the checkpoint
    Results cannot be traced to a runObservabilityOne run ID and the subagent's task ID on every result

    4. Coverage. The report opens with a reconciliation line: 160 services in the catalogue, results received for N, validated M, and the list of services marked "needs human audit". Nothing is reported as complete until the counts match. The access is read-only throughout, which keeps the audit within Northgate's production-access rules.
