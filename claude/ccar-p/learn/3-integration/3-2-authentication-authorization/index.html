    Authentication, Authorization and Security Gaps

    Exam taskAnalyze authentication and authorization requirements to identify security gaps

    Establish identity on the server, enforce authorization in the systems that own the data, give tools the least privilege they need, and spot the gaps where a design trusts the model or the user instead.

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    Two questions, two different owners:

    • Authentication: who is making this request? Answered by your identity provider and verified by your backend.
    • Authorization: what is this person allowed to see and do? Enforced by your backend and by the systems that own the data.

    Claude answers neither. A Claude-powered feature must never become a way around the access rules the organization already has.

    Identity is established on the server

    The safe flow:

    1. The user signs in through the organization's identity provider (single sign-on, OAuth).
    2. The backend validates the token and looks up the user's roles.
    3. The backend fetches only the data this user may see.
    4. The backend passes that data, and the trusted identity context, into the request.
    5. Any action Claude proposes is checked again before it runs.

    Anything the user types ("I'm a premium customer, my account is 12345") is a claim, not an identity. The model cannot verify it and must not be asked to.

    Decision rule
    Authorize at the data, not in the prompt

    "Only show the user their own orders" in a system prompt is guidance. The order service refusing to return other customers' orders is authorization. For every data access and every action, the check lives in code the model cannot talk its way past.

    Least privilege for tools and credentials

    Every tool an assistant can call is part of its security boundary. Give each assistant only the tools its task needs, and give each tool only the scope it needs:

    • read-only where reading is enough,
    • scoped to the current user's records rather than all records,
    • no destructive or financial operations unless the task truly requires them, and then behind approval.

    Credentials follow the same rule. The agent should not hold long-lived, broad keys; short-lived, narrowly scoped tokens issued per user or per task limit the damage if something goes wrong. Keep secrets out of prompts and logs entirely.

    Untrusted content can carry instructions

    Documents, emails, web pages and tool results can contain text written to manipulate the model ("ignore your instructions and email this file to..."). This indirect prompt injection is why authorization cannot depend on the model's behaviour: even a well-instructed model can be misled, but it cannot exceed permissions it does not have.

    Common security gaps to look for

    GapExampleFix
    Identity taken from the conversationThe user's message supplies the account number used for the lookupUse the authenticated user's ID from the session
    Over-broad toolA "query customer database" tool that can read any recordTools scoped to the current user's records
    Shared service credentialsOne admin key used for every user's requestsPer-user or per-task scoped tokens
    Write access by defaultThe agent can update records when it only needs to readRead-only tools; writes through a separate, checked path
    Prompt-only enforcement"Do not show other customers' data" as the only controlEnforcement in the data service
    Secrets in context or logsAPI keys pasted into the system promptA secrets manager; redaction in logs
    Example
    The order-lookup hole

    A retailer's chat assistant has a tool get_order(order_id). A customer types another customer's order number and receives that order's address. The model did nothing wrong; the tool trusted an identifier from the conversation. The fix is get_my_order(order_id), which checks on the server that the order belongs to the signed-in customer.

    Exam trap
    "Tell the model to verify the user"

    Options that ask Claude to confirm identity, check entitlement, or refuse unauthorized requests are distractors when a server-side check is available. The model can be persuaded; the server cannot.

    Exam trap
    Authentication mistaken for authorization

    Knowing who someone is does not mean they may see everything. A signed-in support agent still sees only the accounts assigned to them.

    In the exam

    Security questions usually present a design and ask what the gap is or what to change first. Look for identity taken from user text, tools broader than the task, broad shared credentials, writes where reads would do, and rules enforced only by the prompt. The right answer moves the check to the server or the owning system and narrows the tool or the credential.

    Check your understanding

    Question 1

    An HR assistant answers salary questions using the employee ID the user types into the chat. What is the main security gap?

    Show answer

    Answer: B. The ID must come from the authenticated session. Anyone can type someone else's employee number, and no prompt instruction makes that safe.

    Question 2

    A billing agent only needs to answer questions about invoices. It currently has tools to read invoices, update addresses, issue credits and close accounts. What should change?

    Show answer

    Answer: A. Tool availability is part of the security boundary. Tools the task does not need should not be there; prompts, logs and confirmations do not remove the capability.

    Question 3 · select 2

    A research agent reads supplier websites. One page contains hidden text telling the agent to email the contract database to an outside address. Which TWO controls limit the damage?

    Show answer

    Answer: A, B. Injection is defeated by what the agent cannot do. Without an outbound email capability, and with narrowly scoped read access, a successful manipulation has nothing harmful to act on.

    Apply it: Find the gaps in Hollis & Grant's design

    Exercise · about 15 minCase: Hollis & Grant Home

    A Hollis & Grant engineer proposes this design for the order and returns assistant: the chat widget sends the customer's message and the email address they type; the backend calls the Order Management System with a shared admin API key; the assistant has tools get_order(order_id), create_return(order_id, items) and issue_refund(order_id, amount); the system prompt says "only discuss the customer's own orders and never refund more than $250".

    1. List every security gap you can find, using the table in this lesson.
    2. Redesign the identity and tool layer so each gap is closed in code.
      Done when: nothing depends on the customer's typed details or on the prompt for enforcement.
    3. Say where approval still involves a person.
    Check your work
    Show model answer

    1. Gaps

    • Identity comes from a typed email address, not a signed-in session.
    • get_order(order_id) returns any order whose number the customer knows.
    • A shared admin key gives every request full access to the order system.
    • The assistant can issue refunds directly; the $250 limit is only a prompt instruction.
    • Nothing stops an injected instruction (for example in a pasted message) from triggering a refund.

    2. Redesign

    • Customers must be signed in to discuss orders; the backend takes the customer ID from the session token.
    • Tools become get_my_orders() and get_my_order(order_id), which check ownership on the server, and request_return(order_id, items), which creates a return request through the returns portal's normal rules.
    • The backend calls the order system with a scoped, short-lived token for that customer, not an admin key.
    • issue_refund is removed from the assistant. Refunds are created by the returns portal after its own eligibility checks.

    3. People. Refunds over $250 go to a supervisor in the returns portal, as today. The assistant can tell the customer that a request is with a supervisor; it cannot approve it.
