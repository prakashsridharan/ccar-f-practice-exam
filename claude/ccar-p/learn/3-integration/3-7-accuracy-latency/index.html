Accuracy-Latency Trade-offs

Exam taskEvaluate accuracy-latency trade-offs and justify configuration decisions

Know which configuration settings move accuracy and which move latency, find the setting that holds up the tightest budget, and justify each choice with measurements rather than preference.

On this pageWhat you need to knowIn the examCheck your understandingApply itSources

What you need to know

Most configuration choices trade accuracy against latency (and usually cost). The architect's job is to know which dial moves which outcome, find the constraint that is actually tight, and defend each setting with numbers.

The dials

SettingEffect on accuracyEffect on latency
Model tierLarger tiers handle harder reasoningLarger tiers are slower
Extended thinking and effortOften better on multi-step problemsAdds thinking time and tokens
Prompt and context sizeRelevant context helps; clutter hurtsMore input takes longer to process
Prompt cachingNo changeFaster on cache hits
Retrieval depth and rerankingMore candidates and reranking find better passagesEach adds a step
Sequential versus parallel tool callsNo changeIndependent calls in parallel finish sooner
Output length limitsToo short truncates answersShorter outputs finish sooner
StreamingNo changeMuch faster perceived latency: the first words arrive early
Batch processingNo changeMuch slower (hours), much cheaper; for work no one waits on

Find the load-bearing setting

When a design has both a latency target and an accuracy target, one of them is usually binding. Ask: which setting, if relaxed, would break the tightest budget? That is the setting to protect, and the one to justify most carefully.

  • If latency is binding: keep thinking low or off, use a faster tier where the evaluation allows, cache the stable prefix, run independent tools in parallel, stream the response, and skip reranking unless retrieval quality demands it.
  • If accuracy is binding: spend latency where the evaluation shows a gain (a stronger tier, more thinking, reranking) and recover time elsewhere (caching, parallel calls, streaming, fewer retrieved chunks).
Decision rule
Measure the tail under load

Latency targets are about the 95th or 99th percentile with realistic concurrency, not one request on a quiet afternoon. Accuracy targets are about the evaluation set, not a demo. Justify every setting with both numbers.

Perceived versus actual latency

Streaming does not make the full answer arrive sooner, but users see progress within a fraction of a second, which is what most chat experiences need. For a backend step whose output is parsed before anything is shown, streaming does not help; the full time is what counts.

Different routes, different settings

One application rarely needs one configuration. A chat route may use a small tier, no thinking and streaming; a nightly analysis job on the same data may use a larger tier, more thinking and batch pricing. Configure per route, not per application.

Example
Meeting a 3-second target

A chat assistant on the balanced tier with thinking enabled had a 95th-percentile response time of 5.8 seconds. The evaluation showed thinking added no measurable accuracy on its question types. Turning thinking off, caching the 6,000-token prefix, calling the order and returns tools in parallel and streaming the reply brought the 95th percentile to 2.4 seconds with first words in under a second, and accuracy unchanged.

Exam trap
Streaming as a fix for backend latency

Options that add streaming to a step whose output must be complete before the next step runs do not reduce the latency that matters.

Exam trap
Turning everything up "for quality"

A design that uses the largest tier, maximum thinking and reranking everywhere will rarely meet a real-time target. Spend latency only where the evaluation shows it buys accuracy.

In the exam

These questions give targets for latency, accuracy and sometimes cost, and a configuration that misses one. Identify the binding constraint, then pick the change that moves it without breaking the others: thinking, tier, caching, parallel tools, streaming, reranking or batch. Answers that justify the change with a measurement on the right percentile are usually the strongest.

Check your understanding

Question 1

A chat assistant meets its accuracy target, but users complain it feels slow. Full answers take 4 seconds. Which change improves the experience most cheaply?

Show answer

Answer: D. Users experience the time to the first words. Streaming cuts perceived latency without touching accuracy; the other options leave latency the same or make it worse.

Question 2

An agent calls three independent APIs one after another, each taking about 800 ms. What reduces latency without affecting accuracy?

Show answer

Answer: C. Independent tool calls can run at the same time, saving over a second per turn with no change to what the model sees or decides.

Question 3 · select 2

A nightly job analyses 20,000 documents with no user waiting. Which TWO choices fit?

Show answer

Answer: A, D. With no one waiting, latency is not binding. Batch pricing cuts cost, and the time budget can go to whatever improves accuracy.

Apply it: Justify Hollis & Grant's chat configuration

Exercise · about 15 minCase: Hollis & Grant Home

Hollis & Grant's chat route must reply within 3 seconds at the 95th percentile and stay within its accuracy threshold. A test at peak load shows: balanced tier, extended thinking on, no caching, order and returns tools called one after the other, hybrid retrieval with reranking on every product question, no streaming. Results: 95th-percentile latency 6.1 seconds; accuracy 2 points above the threshold.

  1. Name the binding constraint and explain how you know.
  2. List the changes you would make, in order, with the effect you expect from each.
    Done when: each change says whether it affects accuracy, latency or both.
  3. Say what you would measure before accepting the new configuration.
Check your work
Show model answer

1. Binding constraint. Latency: it misses by more than 3 seconds, while accuracy has a 2-point margin. Any change may spend at most that margin.

2. Changes, in order

ChangeExpected effect
Cache the 6,000-token stable prefixFaster on every request; no accuracy change
Call the order and returns tools in parallelRemoves one round trip on returns contacts; no accuracy change
Stream the replyFirst words under a second; full time unchanged
Evaluate with thinking offLikely the largest saving; accept only if accuracy stays above threshold
Rerank only when the top hybrid results are close in score, or rerank fewer candidatesSaves a step on most product questions; check retrieval recall
Small tier for order-status phrasing onlyFaster on the highest-volume route; facts come from the tool, so risk is low

3. Before accepting. A peak-load test reporting 95th-percentile total latency and time to first words, the full accuracy evaluation with the product-question slice reported separately, and retrieval recall with the new reranking rule. Accept only if latency is under 3 seconds and accuracy is still above threshold.
