Observability at Scale

Exam taskAnalyze observability challenges and select monitoring strategies at scale

Instrument Claude integrations so any answer can be traced end to end, costs and limits can be attributed to the right team or tenant, and problems are detected before users report them.

On this pageWhat you need to knowIn the examCheck your understandingApply itSources

What you need to know

When a Claude-powered feature gives a wrong answer at 2 a.m., someone has to find out which model, prompt, inputs, tools and user produced it. At scale, with many routes, tenants and agents, that is impossible without deliberate instrumentation.

Log four kinds of information per call

CategoryFields
RequestModel and version, prompt template version, input tokens, which tools were offered
ResponseOutput tokens, latency (total and time to first token), stop reason, tool calls made
ContextTrace ID, user role (not raw identity where avoidable), tenant, session, whether the cache was hit
OutcomeDid the downstream system accept the result? Did the user escalate, correct or rate it?

Outcome is the field most often missing, and the one that connects technical behaviour to business results.

Four layers of observability

  1. Request tracing. One trace ID follows a request from the gateway through retrieval, every model call, every tool call and every subagent. Standard tracing tools (such as OpenTelemetry) let agent traces join the application's existing traces.
  2. Metric aggregation. Latency percentiles, error rates, token use, cost, cache hit rate and outcome rates, per route and per tenant.
  3. Anomaly detection. Alerts on changes from the baseline: a jump in escalations, a fall in cache hits, a cost spike for one tenant, a rise in a particular stop reason.
  4. Change attribution. Every deploy, prompt version, model change and configuration change is recorded, so a shift in a metric can be tied to its cause.
Decision rule
Version everything that can change behaviour

If the logs cannot say which prompt version and model handled a request, a regression cannot be traced to its cause. Prompt and configuration versions belong in every log line.

Attribution and isolation

At scale, you need to know who is using capacity and money, and to stop one consumer from starving others.

  • Separate keys or workspaces per team, product or tenant let usage, cost and rate limits be tracked and capped separately. One shared key hides who caused a spike, and one heavy tenant can exhaust a limit everyone shares.
  • Usage and cost reporting by key or workspace feeds chargeback and budget alerts.
  • Per-tenant dashboards and limits in your own application add a second layer for products that serve many customers.

Privacy in the logs

Logs and traces can become the biggest store of sensitive data in the system. Decide what is recorded: redact or hash personal data, avoid full prompt and response bodies where metadata is enough, restrict access, and set retention to match policy. Trace exporters usually let you control whether message content is included.

Example
The tenant nobody could see

A SaaS company served 60 customers from one API key. One customer's bulk import loop sent 40,000 requests in an hour, the shared rate limit was hit, and every other customer's assistant began failing. Nobody could tell which customer caused it from the provider's usage view. Moving to per-tenant workspaces with their own limits, and tagging every trace with the tenant ID, made the next incident visible in minutes and confined to the tenant that caused it.

Exam trap
Logging only errors

Many failures are not errors: the model answers fluently and wrongly, or the user gives up. Without outcome signals, these never show up.

Exam trap
Full transcripts by default

Storing every prompt and response verbatim "for debugging" can breach privacy rules and multiply the sensitive data the company holds. Log what is needed, protected and time-limited.

In the exam

Observability questions describe an incident that could not be diagnosed, a cost or rate-limit problem that could not be attributed, or a multi-agent run whose failure could not be traced. The answer adds the missing piece: trace IDs across components, versioned prompts and models in logs, outcome signals, per-tenant keys or workspaces, or anomaly alerts. Watch for answers that log everything verbatim without regard to privacy.

Check your understanding

Question 1

A shared API key serves 40 business customers. One customer's traffic spike causes rate-limit errors for all of them. What design prevents this?

Show answer

Answer: B. Separate keys or workspaces isolate tenants' limits and make usage attributable. A higher shared limit only delays the same problem.

Question 2

Quality dropped on Tuesday afternoon. Logs show model, tokens and latency, but not which prompt version served each request. What is missing?

Show answer

Answer: A. To link a quality change to its cause, logs must record which prompt and configuration version handled each request, alongside deploy history.

Question 3 · select 2

Which TWO signals catch a fluent but wrong answer that raised no error?

Show answer

Answer: B, C. Outcome signals reveal silent failures. A wrong answer usually returns a successful status and normal token counts.

Apply it: Instrument Northgate's in-product assistant

Exercise · about 20 minCase: Northgate Software

Northgate's in-product assistant will serve 60 banks, from 40 users to 4,000. Each bank must only see its own data, AI usage is billed back per bank, and the assistant calls Claude, two internal services and sometimes a subagent for long reports.

  1. List the fields every trace and log line must carry.
  2. Design attribution and isolation across the 60 tenants.
    Why: chargeback and fairness both depend on it.
  3. Pick four metrics with alert conditions.
  4. Set the privacy rules for what is logged and for how long.
Check your work
Show model answer

1. Fields. Trace ID (shared with the subagent and the internal services), tenant ID, user role, route, model and version, prompt template version, input and output tokens, cache hit, latency and time to first token, stop reason, tools called, and outcome (accepted, edited by the user, rejected, escalated).

2. Attribution and isolation. One workspace and API key per bank, with a spending limit and rate limit sized to its contract; the provider's usage and cost reports by workspace feed monthly chargeback. Inside the product, per-bank request quotas protect the platform from a runaway client, and every data-access tool is scoped to the calling bank's tenant ID on the server.

3. Metrics and alerts

MetricAlert when
95th-percentile latency per routeAbove target for 15 minutes
Cost per bank per dayAbove 150% of its 30-day average
Rate-limit errors per bankAny sustained occurrence
Rejected or edited outputsUp 5 points on the 7-day baseline, especially just after a prompt or model change

4. Privacy. No full prompts or responses by default; log metadata and hashed identifiers. A sampled, redacted content store for quality review, access-controlled and kept for 30 days. Trace exports configured to exclude message content. Retention for operational logs set by Northgate's SOC 2 policy, and nothing from one bank visible to another bank's support staff.
