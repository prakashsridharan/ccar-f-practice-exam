    Configuring Claude Tools for Teams

    Exam taskConfigure Claude tools and environments for teams (e.g., Claude Code)

    Set teams up with a shared, enforced Claude Code configuration, distribute Skills through the mechanism that fits each audience, bound spending up front, and roll out through champions rather than a single big launch.

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    Giving every engineer access and letting each one configure Claude Code alone produces forty different setups, uneven results and no way to enforce anything. Team setup is an architecture decision with four parts: shared configuration, distribution of reusable assets, spend posture and rollout.

    Shared configuration: guidance versus enforcement

    Claude Code reads configuration at several levels, and the difference between them matters.

    LayerWhat it doesUse for
    Organization-managed settingsSet by administrators; override user and project settingsRules that must hold everywhere: denied commands and paths, allowed tools, approved model choices
    Project settings (in the repository)Shared by everyone working in that projectProject permissions, hooks, MCP servers the project needs
    Instruction files (CLAUDE.md) at organization, project and user levelLoad standing context and conventions into every sessionCoding standards, repository layout, how to run tests
    User settingsPersonal preferencesEditor habits, personal shortcuts

    Instruction files are guidance: Claude follows them, but they cannot prevent an action. Permissions, managed settings and hooks are enforcement. Anything that must never happen ("never read .env files", "never push to main") belongs in permission rules or hooks, not only in an instruction file.

    Decision rule
    Put musts in settings, shoulds in instructions

    If breaking a rule would be an incident, enforce it with managed settings, permissions or a hook. Instruction files are for conventions and context.

    Distributing reusable assets

    MechanismReachesVersioning and rollbackFits
    Project Skills in the repositoryEveryone working in that repositoryVersioned and rolled back with the repositoryOne team's procedures and conventions
    Plugins managed for the organizationChosen groups or the whole organizationVersion-controlled updates; can be required, installed by default or optionalGoverned procedures and tool sets for specific teams
    Organization-provisioned SkillsEveryone in the organizationCentral availability, more limited version controlCapabilities everyone should have
    API SkillsYour own products, programmaticallyVersion pinning in the calling systemMachine-to-machine reuse

    Choose by who needs it and how much control over updates and rollback you need. A shared asset with no way to roll back can push one bad change to every engineer at once.

    Spend posture

    Decide the limits before usage grows: default model and allowed models, guidance on effort or thinking levels, per-user and per-team spending caps, rate limits, and usage reporting. Track usage and outcomes with analytics so spending can be tied to results.

    Rollout: champions, then batches

    1. Pilot with a champion in each team, who adapts the shared setup, finds the useful workflows and writes them down.
    2. Expand in batches, team by team, with the champion supporting each batch.
    3. Measure and adjust: usage, outcomes (cycle time, review findings), costs and feedback, before the next batch.

    Two failure patterns to avoid: lumpy adoption (a few heavy users, everyone else idle, so practice never standardizes) and stalling at chat (teams use it to ask questions but never adopt repository-aware workflows, Skills or tool integrations, because nobody enabled them).

    Example
    A rule that was only a suggestion

    A team's CLAUDE.md said "never modify files under /migrations". After an engineer approved a batch of edits without reading them, a migration file changed. The rule moved into a deny permission in the project settings, plus a hook that blocks any edit to that path, and the instruction file now explains why.

    Exam trap
    Security rules in an instruction file only

    Options that rely on CLAUDE.md to stop secret access, destructive commands or protected-branch pushes are weaker than ones that use permissions, managed settings or hooks.

    Exam trap
    Big-bang rollout

    "Give everyone access on Monday" is usually wrong in a scenario about adoption. Champions and batches turn access into consistent practice.

    In the exam

    Team-configuration questions ask where a rule belongs, which distribution mechanism fits a Skill, how to control spend, or how to roll out. Enforce must-never rules in settings, permissions or hooks; use instruction files for conventions; match distribution to audience and rollback needs; set spend limits up front; and roll out through champions and batches.

    Check your understanding

    Question 1

    Security requires that Claude Code never read files matching .env* in any repository. Where should this live?

    Show answer

    Answer: D. A rule that must hold everywhere belongs in enforced, organization-managed settings. Instructions and training guide behaviour but cannot block a read.

    Question 2

    A release procedure must run identically in six departments, and the platform team must be able to update or roll it back centrally. What fits best?

    Show answer

    Answer: C. Group targeting with central, version-controlled updates and rollback is what organization-managed plugins provide. Copies in many repositories drift.

    Question 3 · select 2

    Which TWO practices prevent "stalling at chat" during a rollout?

    Show answer

    Answer: A, C. Adoption beyond chat needs enablement: people who demonstrate the workflows and a setup that includes Skills and integrations.

    Apply it: Plan Northgate's Claude Code rollout

    Exercise · about 20 minCase: Northgate Software

    Plan how Northgate rolls Claude Code out to 420 engineers in 38 teams, using the case constraints (SOC 2, secrets incidents, restricted production access, $40 per engineer per month).

    1. Split the rules into enforced settings and instruction-file guidance.
      Done when: every rule tied to a past incident or SOC 2 is enforced.
    2. Choose distribution mechanisms for: the secrets checklist Skill, the release procedure, each team's own conventions, and the logging-migration guide.
    3. Set the spend posture.
    4. Write the rollout plan with dates relative to day 1, and the measures that gate each batch.
    Check your work
    Show model answer

    1. Rules

    Enforced (managed settings, permissions, hooks)Guidance (CLAUDE.md)
    Deny reading .env*, key files and the secrets directoryCommit message format
    Deny git push to protected branches; deny force-pushTest conventions per language
    No production credentials or write access in any sessionService layout and where things live
    Approved MCP servers onlyHow to run the local stack
    A hook that scans staged changes for secrets before commitWhen to ask for a security review

    2. Distribution

    AssetMechanism
    Secrets checklist SkillPlugin required for all engineering groups, owned by security
    Release procedurePlugin for the teams that release services, versioned by the platform team
    Team conventionsEach repository's project instructions and project Skills
    Logging-migration guideProject Skill in the monorepo, plus a plugin for the 40 other repositories during the migration window

    3. Spend posture. Balanced tier as default, the top tier allowed on request for specific work; per-user monthly cap at $60 with an alert at $40; team-level reports weekly; analytics tracking usage alongside pull request cycle time.

    4. Rollout. Days 1 to 30: one champion per team (38 people) on the shared setup; they record workflows and issues. Days 31 to 60: first batch of 10 teams, supported by their champions. Days 61 to 120: remaining teams in three batches. Each batch starts only if the previous one shows weekly active use above 60%, no secrets or permission incidents, spend within the cap, and no rise in review rework.
