    Debugging and Operational Support

    Exam taskSupport debugging and operational issue resolution

    Support teams running Claude systems by connecting symptoms to architectural causes, and leave behind runbooks and escalation paths so the team can resolve the familiar problems without you.

    On this pageWhat you need to knowIn the examCheck your understandingApply itSources

    What you need to know

    When a Claude-powered system misbehaves, the architect is often the person who knows why. The fast response is to fix it yourself. The lasting response is to fix it with the team and leave behind what they need to fix the next one alone.

    From symptom to cause

    Most operational symptoms trace back to a small set of architectural causes. Writing the mapping down is the start of a runbook.

    SymptomLikely causesFirst action
    Quality declined gradually with no code changeModel version change, prompt change, retrieval drift as content grew or changedRun the evaluation set; check model, prompt and corpus change history
    Latency spikedContext grew, a tool slowed down, the cache stopped hittingRead traces for the slowest step; check tokens per request and cache hit rate
    Intermittent tool failuresExpired credentials, rate limits, unhandled error pathsTrace one failed call end to end; check auth and limits for that tool
    Cost rose without more usageLarger tier in use, cache regression, growing context, retry loopsCompare model mix, cache hits and tokens per request with the budget model
    Requests rejected or outputs cut offContext too large; output limit too lowCheck the error type and stop reasons; count tokens
    Agent loops or never finishesMissing stopping rule, a tool that keeps failing quietlyRead the trace; check turn limits and tool error handling

    Runbooks

    A runbook entry records: the symptom as the on-call engineer will see it, how to confirm it, the likely causes in order, the first action for each, how to verify the fix, and when to escalate. Good entries are written after real incidents, tested by someone other than the author, and updated when the system changes.

    Decision rule
    Teach the path, not just the fix

    Every incident you resolve should end with a runbook entry the team wrote or reviewed. The goal is a team that needs the architect for new problems, not familiar ones.

    Escalation paths

    People need to know where their responsibility ends. An escalation path names who handles what (first-line on-call, the team owning the AI service, the architect, the platform or vendor) and the conditions for moving up: severity, duration, customer impact, safety or compliance implications. Without it, issues either sit with someone who cannot fix them or go straight to the busiest person.

    Support Claude Code users too

    Engineering teams using Claude Code have their own recurring issues: configuration not loading where expected, permissions blocking a needed command, an MCP server failing to connect, context filling up in long sessions. The same approach applies: a short internal troubleshooting page, champions as first line, and a clear route to the platform team.

    Example
    A slow decline no one connected

    An internal knowledge assistant's answer quality slid over a quarter while dashboards stayed green. The cause was a document library that had doubled in size without the index being rebuilt on the new structure. Nobody on the support rota knew that "gradual decline, no code change" points to retrieval drift. After the fix, the team added that runbook entry and a monthly retrieval-recall check; the next drift was caught in a week.

    Exam trap
    The architect as permanent firefighter

    In support scenarios, the strongest answer usually combines resolving the issue with building the team's ability to resolve it next time: a runbook entry, an escalation path, a monitoring check.

    Exam trap
    Changing the model as a first step

    For drift, latency or cost symptoms, the first action is to look at traces and change history. Swapping models first changes a variable before the cause is known.

    In the exam

    Support questions describe a symptom and ask for the likely cause, the first action, or how to stop the same problem recurring. Use the symptom-to-cause mapping, start with evidence (traces, change history, evaluation runs), and prefer answers that leave behind a runbook entry and a clear escalation path.

    Check your understanding

    Question 1

    An assistant's answer quality has slowly declined over two months. There were no code changes. What is the best first action?

    Show answer

    Answer: D. Gradual decline without code changes points to model, prompt or retrieval drift. Measuring against the evaluation set and checking each history finds which.

    Question 2 · select 2

    Costs rose 50% this month with flat usage. Which TWO checks come first?

    Show answer

    Answer: A, D. Rising cost without rising usage most often comes from cache regressions or a shift to more expensive models. Both show in usage and cost data.

    Question 3

    What makes a team more self-sufficient after an incident the architect helped resolve?

    Show answer

    Answer: C. A runbook entry and a clear escalation path turn one fix into a repeatable capability for the team.

    Apply it: Write Hollis & Grant's assistant runbook

    Exercise · about 20 minCase: Hollis & Grant Home

    Hollis & Grant's assistant is live, and the e-commerce engineering on-call rota will support it. Write the start of their runbook.

    1. Write four runbook entries for symptoms likely in this system, each with confirmation steps, likely causes, first action, verification and escalation condition.
      Done when: at least one entry covers a slow quality decline and one a cost rise.
    2. Write the escalation path: levels, who, and when to move up.
    3. Name the routine checks that would catch problems before they become incidents.

    2. Escalation path. Level 1: on-call engineer, using the runbook. Level 2: the AI service team lead, for anything not covered or not resolved within the runbook's limits.
