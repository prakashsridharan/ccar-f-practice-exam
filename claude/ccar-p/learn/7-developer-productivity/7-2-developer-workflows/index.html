Improving Developer Workflows

Exam taskImprove developer workflows using AI-assisted tooling

Fit AI assistance into the existing development workflow at the stages where it helps, give Claude ways to verify its own work, and keep a review discipline that ensures people still understand what ships.

On this pageWhat you need to knowIn the examCheck your understandingApply itSources

What you need to know

The value of AI-assisted development comes from improving the workflow a team already has, not from bolting a chat window beside it. The architect's job is to put assistance where it helps and to keep the quality bar where it was.

Where assistance fits

StageHow Claude helpsWhat still needs a person
UnderstandingExploring an unfamiliar codebase, explaining code, tracing a flowJudging whether the explanation is right
PlanningProposing an approach and the files to change, before any editApproving the plan
WritingImplementations, tests, boilerplate, refactors from a clear specificationCorrectness, security and design review
ReviewingSummarizing a diff, flagging likely issues, checking conventions in CIThe decision to merge
DebuggingHypotheses from symptoms, logs and tracesConfirming the hypothesis against evidence

Practices that make the output better

  • Explore, then plan, then code. Asking Claude to read the relevant code and propose a plan before editing produces better changes than asking for code straight away. A read-only planning mode helps.
  • Give it a way to check itself. Tests, a build, a linter, a screenshot to compare against: when Claude can run the check, it can find and fix its own mistakes before a person sees them.
  • Small, reviewable changes. Large AI-generated diffs are hard to review well. Break work into steps a reviewer can actually read.
  • Parallel sessions for independent work, each in its own working copy (for example git worktrees), so tasks do not interfere.
  • Automation in CI. Running Claude non-interactively with structured output lets it review pull requests, triage failures or update documentation as pipeline steps, with deterministic checks (hooks, tests) around it.

The verification discipline

AI makes code cheaper to produce, so more of it reaches review. The bar does not move. A team checklist for any AI-assisted change covers:

DimensionThe change passes when
CorrectnessTests cover the requirement and its edge cases, and they pass
SecurityNo secrets, inputs validated, least-privilege access for any new calls
MaintainabilityIt follows team conventions and introduces no unexplained complexity
UnderstandingThe author can explain what it does, why, and how it handles inputs no test covered
Decision rule
The author must understand what ships

Passing tests is not the same as understanding. The person who submits a change is accountable for it, whoever or whatever wrote it.

The risk the last row guards against is judgment erosion: a team that ships code it no longer understands because it looked right and passed shallow checks, until an input nobody reasoned about reaches production.

Measuring the effect

Track workflow outcomes, not just usage: pull request cycle time, review rework, escaped defects, time spent on toil. A tool that speeds up writing but slows down review, or raises defects, has not improved the workflow.

Example
Faster code, slower reviews

After adopting AI-assisted coding, a team's pull requests doubled in size and review time per pull request rose by 70%; cycle time barely improved. Splitting work into smaller changes, asking for a plan before code, and requiring authors to annotate non-obvious generated sections brought review time back down and cut cycle time by a third.

Exam trap
"Tests pass, so it can merge"

Options that treat green tests as sufficient for AI-generated code skip the understanding and security checks. The better option keeps the full review bar.

Exam trap
AI review as the final verdict

An automated review is input to a person's decision, not the decision. Options that let an AI reviewer approve merges on its own are usually wrong.

In the exam

Workflow questions describe a team using AI tooling and a problem: low quality, slow reviews, unclear ownership, uneven use. Strong answers place assistance at the right stage, give Claude a way to verify its work, keep changes reviewable, keep humans accountable with a verification checklist, and measure workflow outcomes rather than usage.

Check your understanding

Question 1

Claude's changes to a service often compile but break behaviour elsewhere. What change helps Claude most?

Show answer

Answer: B. When Claude can run the checks, it can catch and correct its own mistakes. Instructions and explanations do not give it that feedback.

Question 2

A team merges AI-generated pull requests once CI passes and an AI reviewer approves. What is missing?

Show answer

Answer: A. Human understanding and accountability are the guard against judgment erosion. More automation of the same kind does not add it.

Question 3 · select 2

Which TWO practices make AI-assisted changes easier to review well?

Show answer

Answer: A, B. Plans and small changes keep reviews meaningful. Large combined diffs and skipped tests make problems easier to miss.

Apply it: Improve Northgate's pull request workflow

Exercise · about 15 minCase: Northgate Software

Northgate's median pull request cycle time is 26 hours. Three months into the pilot, champions report: AI-assisted pull requests are larger, reviewers struggle with them, and two recent incidents came from generated code that "looked fine" and that the author could not later explain.

  1. Redesign the workflow from task to merge, showing where Claude helps and where people decide.
  2. Write Northgate's verification checklist for AI-assisted changes, with one concrete check per dimension.
    Done when: the understanding check would have caught the two incidents.
  3. Choose three measures to show whether the changes worked.
Check your work
Show model answer

1. Workflow

  1. Engineer asks Claude to explore the relevant code and propose a plan (read-only planning). Engineer approves or edits the plan.
  2. Claude implements in small steps, running tests and the linter itself; the secrets hook blocks any commit with credentials.
  3. Engineer reviews the diff locally and annotates anything non-obvious.
  4. Pull request opened, kept under an agreed size; the CI review bot (lesson 3.1) adds comments.
  5. A human reviewer decides; the author answers review questions themselves.

2. Verification checklist

DimensionCheck
CorrectnessNew behaviour has tests, including at least one failure or edge case, and all tests pass
SecurityNo secrets (hook passes); new inputs validated; new calls use existing scoped credentials
MaintainabilityFollows the service's conventions; no new dependency or abstraction without a reason in the description
UnderstandingThe description explains in the author's words what changed and why, and how it behaves on an input the tests do not cover; the reviewer may ask the author to walk through any generated section

3. Measures. Median pull request cycle time and review time per pull request; pull request size distribution; incidents and reverts traced to AI-assisted changes.
