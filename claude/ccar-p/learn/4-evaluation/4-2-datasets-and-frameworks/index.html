Evaluation Datasets and Test Frameworks

Exam taskDesign evaluation datasets and test frameworks using mixed methodologies

Build a golden dataset that reflects real traffic and its hard cases, and grade it with the cheapest reliable method for each behaviour: code first, a calibrated model judge where interpretation is needed, and people where stakes or novelty demand it.

On this pageWhat you need to knowIn the examCheck your understandingApply itSources

What you need to know

An evaluation framework has two parts: what you test (the dataset) and how you score it (the graders). Getting either wrong produces numbers that look reassuring and mean little.

The golden dataset

A golden dataset is a set of realistic inputs with expected outputs or grading criteria, used to judge every version of the system on the same footing. A useful one covers:

CategoryExample for a claims assistant
Typical casesA routine auto claim with all documents
Edge casesA claim with two vehicles and three policy holders
Ambiguous inputsA description that fits two claim types
Invalid or incomplete inputsNo policy number; unreadable scan
Adversarial inputsText that tries to change the assistant's instructions
Boundary conditionsThe longest documents the system must handle
Negative casesRequests the system should refuse or escalate

Real production data is the best source of inputs (anonymized as required), weighted to match real traffic, with extra cases for rare but important categories. Synthetic cases fill gaps, especially for adversarial and boundary conditions.

Decision rule
The dataset grows with the system

Every production failure, every user correction and every new feature adds cases. A static test set drifts away from reality and stops catching regressions.

Keep two kinds of suite: capability tests that track progress on what the system cannot yet do well, and regression tests that protect behaviour that already works and must stay working.

The grading ladder

Choose the cheapest grader that is reliable for each behaviour.

GraderUse forStrengthsLimits
CodeFormats, schemas, exact values, banned actions, latency, costFast, cheap, deterministicCannot judge meaning or tone
Model judgeFaithfulness, completeness, tone, reasoning qualityScales; handles nuanceCosts money; can be inconsistent; must itself be validated
Human reviewHigh-stakes, novel or disputed judgments; calibrating the judgeThe reference standardSlow, expensive, hard to scale

One system usually uses all three: code checks on every case, a model judge on the interpretive criteria, and humans on a sample and on anything the judge flags as uncertain.

Making a model judge trustworthy

  • Give it a detailed rubric with clear definitions and examples of each grade.
  • Ask for constrained verdicts (a small set of labels such as pass, minor issue, fail) rather than open-ended scores.
  • Ask it to give its reasoning before the verdict, and grade one criterion at a time.
  • Calibrate against a set of human-graded cases and track agreement over time.
  • Prefer a different model or configuration from the one being graded, to reduce bias toward its own style.

Non-determinism

Model outputs vary between runs. Run important cases more than once, and look at pass rates across runs rather than a single result, especially for agents whose paths can differ.

Example
One requirement, three graders

"The summary lists every medication change with the correct dose" is checked in code against the structured medication record. "The summary is faithful to the notes" is graded by a model judge with a rubric. "The summary is clinically safe to send" is reviewed by a physician on a weekly sample and on every case the judge rates as uncertain.

Exam trap
A judge where a parser would do

Options that use a model judge to check whether output is valid JSON, within length or free of a banned field are wasteful and less reliable than code.

Exam trap
A dataset of clean, typical cases

A test set without edge, adversarial and negative cases overstates quality. Prefer the option that adds them, weighted to their real importance.

In the exam

Framework questions ask what the dataset should contain, which grader fits a requirement, or how to make a judge reliable. Strong answers cover hard and adversarial cases, keep the dataset growing from production, apply code first, use a calibrated rubric-based judge for interpretation, and reserve human review for high stakes and calibration.

Check your understanding

Question 1

A team checks whether every response contains the three required sections. Which grader fits?

Show answer

Answer: B. Presence of fixed sections is deterministic, so code is cheapest and most reliable.

Question 2

A model judge's scores swing between runs on the same responses. Which change helps most?

Show answer

Answer: A. Detailed rubrics and constrained verdicts make judges more consistent. Wider scales, self-grading and bundling criteria all make variation worse.

Question 3 · select 2

Which TWO practices keep a golden dataset useful over time?

Show answer

Answer: A, B. A dataset that learns from production and keeps hard categories represented continues to catch real regressions.

Apply it: Build Lakeview's evaluation framework

Exercise · about 25 minCase: Lakeview Regional Medical Center

Lakeview's discharge-summary drafter (lessons 1.5 and 2.4) needs an evaluation framework before the pilot. Design the dataset and the graders.

  1. Design the golden dataset: size, sources, and the categories it must include.
    Done when: the long-stay and high-risk cases have their own slices.
  2. Assign a grader to each requirement: medications match the pharmacy list, pending results are listed, the hospital course is faithful to the notes, no medication changes are suggested, the summary has all required sections, and it is safe to send.
  3. Make the judge trustworthy: rubric, verdicts and calibration.
  4. Set the release rule for the pilot.
Check your work
Show model answer

1. Dataset. 300 past stays, de-identified for the test environment under the privacy officer's rules, sampled to match the real mix of specialties, plus extra cases: 40 long stays (over 80,000 tokens of notes), 30 stays with medication changes during admission, 20 with pending results at discharge, 15 transfers and deaths (summaries with special requirements), and 20 adversarial cases (notes containing copied instructions, contradictory notes). Physician-signed summaries for the same stays serve as references.

2. Graders

RequirementGrader
Medications match the pharmacy listCode: compare against the structured list
Pending results listedCode: compare against the EHR's pending list
Required sections presentCode
No medication changes suggestedCode checks for change language, plus the judge
Hospital course faithful to the notesModel judge with rubric
Safe to sendPhysician review on a weekly sample and on all judge-uncertain cases

3. Judge. A rubric with definitions and examples for "faithful", "minor omission" and "unsupported statement"; one criterion per call; reasoning before a three-label verdict; calibrated on 100 summaries graded by two physicians, with agreement tracked monthly. The judge runs on a different configuration from the drafter.

4. Release rule. Zero medication mismatches and zero suggested changes across the set; pending results complete in at least 99%; faithfulness at least 97% overall and no slice below 95%; physician reviewers rate at least 95% of sampled drafts safe to sign with minor or no edits.
